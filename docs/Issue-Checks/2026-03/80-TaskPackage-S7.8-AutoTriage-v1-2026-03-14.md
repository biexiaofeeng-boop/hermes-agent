# 任务包：S7.8 Auto-Triage（自愈边界与闭环）v1

- 日期：2026-03-14
- 状态：READY
- 建议分支：`codex/s7-8-auto-triage-v1`
- 目标：让 Bots 具备“可控自修复”能力，形成发现-分级-处置-记录-提交闭环。

## 0) 结论先行

1. 常驻能力命名采用 `auto-triage`，默认先判定再行动。  
2. 采用分级边界：`L0/L1` 可自动修，`L2/L3` 只报告不自动改。  
3. 所有修复必须有证据、日志和 git 记录；无证据不得宣称修复完成。  

## 1) 问题定义

当前运行中存在“口头触发即修改”的行为，虽然效率高，但有两类风险：
1. 边界不清：小修与高风险改动容易混淆。
2. 可追溯不足：修复后缺统一记录，影响运营回看与复盘。

## 2) 能力模型

## 2.1 常驻能力
- `auto-triage`：收集异常并完成风险分级。
- `safe-fix`：仅执行低风险补丁。
- `escalate-report`：中高风险输出分析报告与建议，不改代码。

## 2.2 风险分级
- `L0`：单文件语法/脚本小错，自动修复。
- `L1`：低耦合多文件小改，需最小回归通过后自动修复。
- `L2`：核心路由/鉴权/执行链变更，禁止自动修复，转报告。
- `L3`：依赖升级/大规模重构/删除关键文件，禁止自动修复，转报告。

## 3) 标准SOP

1. Detect：捕获异常（日志、失败命令、用户反馈）。
2. Triage：生成 `issue`，输出等级与处置建议（Fix/Report）。
3. Action：
   - Fix 路径：补丁 -> 验证 -> fix日志 -> git提交。
   - Report 路径：分析 -> 风险 -> 建议 -> 下一步。
4. Record：落盘到 `docs/ops/issue/`。
5. Notify：输出结果回执（可扩展 Feishu/GitHub）。

## 4) 记录规范

- Fix 记录：`docs/ops/issue/fix-<topic>-<date>.md`
- Report 记录：`docs/ops/issue/report-<topic>-<date>.md`
- 内容最小字段：
  - 现象
  - 分级结果（L0~L3）
  - 处理动作
  - 验证证据
  - 后续建议

## 5) 验收硬门槛

1. L2/L3 请求不得进入自动修复路径。
2. L0/L1 自动修复必须附验证证据。
3. 每次处置必须写 issue 文档并可追溯到提交。
4. 用户窗口默认简洁回执，详细过程进文档与日志。

## 6) 回滚策略

1. 一键关闭 `auto-triage.enabled=false`，恢复手动模式。
2. 保留 issue 文档与提交历史，不删除追溯链路。
3. 对误判规则可单独回滚策略文件，不回滚业务代码。
