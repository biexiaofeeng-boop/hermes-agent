# 任务包：S8.1 Memory Recall M1（最小实现，v1）

- 日期：2026-03-25
- 状态：DONE
- 建议分支：`codex/s8-1-memory-recall-m1`
- 目标：在不增加系统复杂度与运行时负担的前提下，提升“长历史记忆召回”稳定性与可验证性。

## 0) 结论先行

1. 本轮只做 M1：检索层最小增强，不做重型 RAG 架构改造。
2. 验收以“回测数据 + 性能门禁 + 回滚演练”三线并行，确保可上线。
3. 默认灰度开关，不影响其他并行版本推进。

## 1) 问题定义

现状（代码事实）：
- 召回候选先按时间倒序截断，再做重排，长历史记忆进入候选池概率低。
- 默认上下文偏 `anchor_only`，导致长期 episodic 记忆在常规会话里曝光不足。
- embedding 依赖缺失时会降级，缺少显式可观测指标。

影响：
- 长历史记忆“有存储、弱可达”，用户体感为“记忆不稳”。
- 回忆结果偏近期，跨周期复盘能力不足。

## 2) 目标与边界

## 2.1 本轮目标（必须）

1. 建立可复现回测集与评估脚本（离线）。
2. 实现 recall 候选池最小增强（近期桶 + 历史桶），降低“近期截断偏置”。
3. 建立性能门禁：P95 延迟与 CPU 开销必须在可控范围。
4. 建立回滚门禁：开关可一键回退至旧逻辑。

## 2.2 非目标（本轮不做）

1. 不引入外部向量库（FAISS/Chroma 等）。
2. 不重构记忆 schema（不做破坏性迁移）。
3. 不改工具接口（`remember/recall/anchor/heartbeat` 参数保持兼容）。
4. 不做跨服务分布式检索。

## 3) M1 方案（最小改动）

1. 检索候选改为双桶：
- Recent bucket：近 7/30 天固定窗口。
- Historical bucket：早期样本固定窗口（按时间分层抽样）。

2. 保留现有评分框架，新增轻量时序项：
- 不改变主权重结构，仅补充可解释时间衰减项。

3. 引入运行期开关（默认关闭）：
- 建议：`NANOBOT_MEMORY_RECALL_M1=0|1`
- `0` 走旧逻辑；`1` 走新逻辑。

4. 最小观测输出：
- `encoder_available`
- `recall_candidate_recent_count`
- `recall_candidate_history_count`
- `recall_latency_ms`

## 4) 回测设计标准（本轮强制）

## 4.1 数据基线

1. 生成固定回测样本（脱敏）：
- 近期样本（0~7 天）
- 中期样本（8~30 天）
- 长期样本（31~180 天）
- anchor/belief 样本

2. 每条 query 配置期望命中集合（qrels），形成可重复评估集。

## 4.2 指标门槛

1. 召回质量：
- Long-history Recall@5 相对基线提升 >= 25%
- Overall NDCG@5 不低于基线（允许 ±3% 波动）

2. 性能：
- recall P95 latency 增幅 <= 10%
- 单次 recall 候选上限固定（避免无界增长）

3. 稳定性：
- encoder 缺失场景不报错，且结果可用
- 开关关闭时完全回退旧行为

## 4.3 回测案例矩阵

1. R01：近期检索不回归（短期问题）
2. R02：长历史检索提升（跨 30 天以上）
3. R03：跨项目检索稳定（project 过滤有效）
4. R04：anchor 记忆可达（belief/fact 不丢）
5. R05：encoder 缺失降级（无异常）
6. R06：性能回归（P95 门禁）
7. R07：开关回滚（old/new 一键切换）

## 5) 风险与回滚

1. 风险：候选池扩大导致延迟波动。
- 控制：固定双桶上限 + P95 门禁。

2. 风险：评分项过多导致调参复杂。
- 控制：M1 仅小幅增量，不引入新依赖。

3. 回滚策略：
- 开关置 `0` 即回退旧逻辑；
- 若必要，代码回滚至变更前快照。
