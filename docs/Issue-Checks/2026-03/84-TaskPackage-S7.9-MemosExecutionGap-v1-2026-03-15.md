# 任务包：S7.9 Memos Execution Gap（v1）

- 日期：2026-03-15
- 状态：READY
- 建议分支：`codex/s7-9-memos-execution-gap-v1`
- 目标：消除“已执行叙事”与“真实落盘状态”之间的错位，保证对用户可见、可追溯、可验证。

## 0) 结论先行

1. 这是执行闭环缺口，不是单纯文案问题。
2. P0 先修“回执可见性 + 失败语义标准化 + 证据门禁覆盖”。
3. P1 再扩展“执行宣称识别”和长期观测指标。

## 1) 问题定义

运行态出现 3+ 次 `memos:local_fallback`。在部分场景中：
- 用户看不到明确失败回执（silent receipt）；
- 叙事层可能继续输出“已完成”语义；
- 实际仅本地暂存，远端未写入。

这会造成“执行已完成”的感知偏差，属于 P0 可靠性问题。

## 2) 根因定位

- Followup 异步链中，memos write 与主回复分离，失败信号没有稳定投递到用户面。
- `TG_RECEIPT_SKIPPED` 在默认静默策略下会吞掉关键状态。
- 执行宣称门禁当前偏通用，对 memos 场景覆盖不足。

## 3) 交付边界（P0/P1）

## 3.1 P0（本轮必须）

1. Memos 非远端成功时，强制可见回执（不得 silent）。
2. 状态文本标准化：明确区分 `remote_success` 与 `local_staged`。
3. 执行宣称门禁扩展到 memos 关键语义。
4. 补齐回归测试（失败回退、可见回执、文案一致性）。

## 3.2 P1（可选项，当前暂不执行）

1. 增加 trace 指标：`memos_fallback_visible_rate`。
2. 增加运营观察脚本，按日汇总 fallback 与人工纠偏次数。

> 维护决策（2026-03-17）：以上两项转入“可选项 backlog”，不作为当前发布阻塞条件。

## 4) 实施顺序

1. 回执策略修复（可见性优先）。
2. memos 结果映射修复（语义一致）。
3. 执行宣称识别扩展。
4. 单测与最小回归。
5. 文档与索引回填。

## 5) 验收硬门槛

1. 任意 `stored != remote` 场景，用户端必须收到失败/降级回执。
2. 不允许“远端未成功但文案呈成功”的输出。
3. 测试覆盖 fallback + receipt + claim guard 三条主链。
4. 运行期问题单状态从 `Resolved` 调整为 `Mitigated`，直到代码修复上线并验证通过。

## 6) 回滚与风控

1. 可通过配置开关回退到旧回执策略（仅紧急）。
2. 回滚后必须保留 `memos:local_fallback` 告警与 issue 记录。
3. 不改动主能力边界，只修执行反馈链，不影响其他通道行为。
