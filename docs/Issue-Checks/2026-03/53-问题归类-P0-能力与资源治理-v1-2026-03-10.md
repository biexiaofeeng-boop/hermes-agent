## 1) 结论总览（Root Causes）

### R1 语义断层（治理层 vs 执行层）
- 现象：`toolchain/capability` 已显示 `tool:websearch-tavily=ready`，但执行层 `web_search` 默认仍调用 Brave。
- 直接后果：运营检查通过，但真实执行路径与预期不一致。
- 代码锚点：
  - 执行工具默认实现：`nanobot/agent/tools/web.py`
  - 主/子 Agent 注入：`nanobot/agent/loop.py`、`nanobot/agent/subagent.py`
  - Toolchain 能力定义：`nanobot/chimera_bridge/toolchain.py`
  - Capability 映射：`nanobot/capability/sync.py`

### R2 配置断层（Config/Secrets 不统一）
- 现象：不同入口脚本对 `secrets.env` 注入不一致，`ops_check / acceptance / gateway` 可能出现环境漂移。
- 直接后果：日检通过率和真实运行状态偶发不一致，排障成本高。
- 代码锚点：
  - 配置解析：`nanobot/config/schema.py`
  - 运维巡检入口：`deploy/chimera_ops_check.sh`
  - 每日检查入口：`deploy/chimera_daily_readiness.sh`
  - S8 验收入口：`deploy/s8-ops-pack/chimera_s8_acceptance.sh`

### R3 资源断层（资源能力定义分散）
- 现象：workspace / missionWorkspace / memory / 外接 SSD 的边界在多个模块分散表达。
- 直接后果：执行边界可解释性不足，容易出现“可执行但不该执行”的路径。
- 代码锚点：
  - missionWorkspace 解析：`nanobot/agent/subagent.py`
  - 上下文组装：`nanobot/context/assembler.py`
  - 路由：`nanobot/context/router.py`
  - 运行时 profile/workspace：`deploy/chimera_profile.sh`

## 2) 优先级分层

### P0（本轮必须完成）
1. Tavily-first 默认链路落地（含降级策略）。
2. secrets 注入入口统一标准化。
3. 资源能力边界基线（优先级、保护规则、巡检项）固化。

### P1（下一轮优化）
1. 多搜索源策略（quality/cost 模式）。
2. 更细粒度资源 ACL（目录级别策略模板化）。
3. 运维 UI 可视化（能力与资源态势板）。

## 3) 设计原则（给 Plan/Dev 统一约束）
1. 一致性优先：治理层 ready 必须映射执行默认路径。
2. 可回滚优先：每一步改动都需有回退开关与命令。
3. 可观测优先：状态、策略、异常都要能被巡检脚本和日志观察到。
4. 小步迭代：避免一次性大改，按阶段交付。

## 4) 方案边界
- In Scope：搜索默认策略统一、secrets 注入统一、资源边界与巡检标准化。
- Out of Scope：新执行器研发、复杂检索编排、跨项目模板体系重构。

## 5) 对开发 codex 的输入摘要
1. 先做“语义对齐”：`capability ready == execution default`。
2. 再做“入口统一”：所有运维入口同一 secrets 加载逻辑。
3. 最后做“边界固化”：资源优先级与保护规则写进配置和巡检。
