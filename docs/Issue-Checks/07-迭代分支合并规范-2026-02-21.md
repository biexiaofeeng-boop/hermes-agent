# 迭代分支与合并规范（2026-02-21）

## 目标
- 每次迭代先在独立分支开发，避免直接改 `master`。
- 保留可回滚快照，确保线上稳定。

## 标准流程（必做）
1. 从 `master` 拉最新后创建分支：`codex/feature-<topic>`。
2. 在 feature 分支完成开发 + 自动测试 + 人工验收。
3. 同步验收文档到 `docs/Issue-Checks/`。
4. feature 分支提交完成后，由 sourcefire 确认是否合并到 `master`。
5. 合并后打版本快照 tag：`snapshot/<topic>-YYYYMMDD-HHMM`。

## 协同标准补充（2026-03-06）
- `master` 仅用于集成与发布，不作为日常开发分支。
- 文档改动与代码改动同等执行“分支优先”，禁止在 `master` 直接编辑 `docs/Issue-Checks/` 后长期滞留。
- 新任务默认流程：
  1. `git fetch origin && git checkout -b codex/<topic> origin/master`
  2. 开发与文档同分支推进（任务包/Checks/脚本/索引回填一起提交）
  3. 完成后由 sourcefire 决定合并窗口
- 例外策略：
  - 若出现紧急热修（生产阻断），允许 `codex/fix-*` 快速修复；修复后必须补齐 Issue-Checks 文档与回滚点。

## 命名约定
- 功能分支：`codex/feature-xxx`
- 修复分支：`codex/fix-xxx`
- 快照标签：`snapshot/<topic>-YYYYMMDD-HHMM`

## 合并门禁
- 自动化测试通过（`deploy/chimera_core_test.sh`）。
- 关键人工用例通过或明确标记 deferred。
- 变更说明、验收结论、风险回滚点已入文档。

## 回滚策略
- 轻量回滚：切回最近快照 tag。
- 热修复：从 `master` 开 `codex/fix-*` 分支修复，复测后再合并。
